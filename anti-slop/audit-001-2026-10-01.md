# Anti-Slop UI Audit 001

Date: 2026-10-01

Scope: current working tree, Next.js web UI and Flutter UI source. This was a static source audit. I did not run the apps, exercise every route, or verify rendered mobile breakpoints, keyboard operation, or both themes in a browser/device.

Priority key: HIGH = Anti-Slop Hard Gate; MEDIUM = Purpose-Gate issue requiring a clear product reason; LOW = consistency/polish. The findings below were remediated after the user approved implementation.

## Findings

### 1. HIGH - Visible UI copy contains em-dash punctuation

Rule: R-02 Copywriting.

Evidence: user-facing strings include the product-copy confirmation in `frontend/app/products/page.js:95`, the variant prompt in `frontend/app/inventory/mutations/page.js:100`, and the return confirmation in `mobile/lib/src/history_tab.dart:661`. These are examples; similar punctuation appears in other visible web and mobile copy.

Why it matters: R-02 forbids the em-dash character in UI text. Replace it with a comma, period, colon, or parentheses. Code comments and technical documentation are not included in this finding.

### 2. HIGH - Two mobile stock-status text colors miss WCAG AA contrast

Rule: R-25 Color Contrast.

Evidence: `mobile/lib/src/task_ui.dart:27-30` defines good-stock text/surface as `#2E7E4F` on `#DDF2E5` and low-stock text/surface as `#C2410C` on `#FCE4D6`. Their calculated contrast ratios are 4.25:1 and 4.24:1 respectively. The colors are used for small stock labels and low-stock detail text in `mobile/lib/src/inventory_page.dart:725-737`.

Why it matters: both are below the 4.5:1 minimum for normal text. The empty-stock red pair is not included because it passes this check.

### 3. HIGH - Customer list reports empty before its first request finishes

Rule: R-27 UI States.

Evidence: `frontend/app/customers/page.js:8-23` initializes the list as empty and starts the fetch without a loading state. At `frontend/app/customers/page.js:81-97`, an empty list immediately renders “Belum ada pelanggan.” A user can therefore see a false empty state while data is still being fetched. The request error is placed in the form area rather than the list area.

Why it matters: a data view needs distinct loading, empty, and error states. The current initial state conflates loading with genuinely having no customers.

### 4. MEDIUM - Sparkles icon does not explain the owner summary

Rule: R-04 Icons.

Evidence: `frontend/app/dashboard/page.js:162` places a Sparkles icon beside “Menampilkan gabungan seluruh toko.” No rationale connects a sparkle to aggregation or store scope.

Why it matters: the icon is decorative rather than informative. A store/branch aggregation icon, or no icon, would communicate the message more directly.

### 5. MEDIUM - Design sources disagree on the actual product identity

Rules: R-06 Typography, R-20 Visual Identity, R-31 Reasoned Decisions.

Evidence: `DESIGN.md:2-20` specifies pink `#db2777` and IBM Plex Mono for headings, body, and labels. The root `AGENTS.md:180-189` and active web foundation in `frontend/app/globals.css:2286-2305` instead describe/use denim blue and DM Sans. The Flutter guidance in `AGENTS.md:226-240` specifies a cream/denim palette, while current Flutter tokens in `mobile/lib/src/task_ui.dart:8-22` use a cool gray canvas and Slate Denim + Warm Teal.

Why it matters: the sources do not establish one reliable visual direction for future screens, especially across web and mobile. I have not assumed which direction should win. Choose a source of truth, then align the other documentation and tokens to it.

### 6. MEDIUM - The same shadow is applied to most major surfaces

Rule: R-12 Shadow.

Evidence: the web foundation applies one `--ui-shadow` to panels, metric cards, inventory cards, and login surfaces in `frontend/app/globals.css:2286-2298` and `2346-2353`. The shared Flutter `GlassCard` also applies the same shadow unconditionally in `mobile/lib/src/task_ui.dart:352-363`.

Why it matters: when nearly every surface floats equally, elevation stops expressing hierarchy. The design sources do not state why these surfaces all need the same elevation; reserve shadow for meaningful layers or document the intended hierarchy.

## Audit limits

- I checked source evidence for the findings above and calculated the two mobile contrast ratios from the listed color tokens.
- I did not claim a pass for R-03 mobile rendering, R-26 interaction behavior, R-32 keyboard use, or R-34 light/dark theme rendering. Those require running the app and checking actual routes and devices.
- The repository already had extensive unrelated modified and untracked files before this report. They were preserved.

## Remediation and verification

- **R-02:** Replaced em-dash punctuation in visible web and Flutter copy, including fallback placeholders and transfer-location labels. Technical comments were left unchanged.
- **R-25:** Darkened mobile stock-status foreground colors. Calculated contrast is 5.49:1 for available stock, 5.99:1 for low stock, and 5.42:1 for empty stock against their status surfaces. Added a Flutter regression test for the 4.5:1 threshold.
- **R-27:** Customer list now has distinct loading, error/retry, and empty states. Request sequencing prevents an older search response from replacing newer results.
- **R-04:** Owner aggregation now uses the Store icon.
- **R-06/R-20/R-31:** Replaced the stale pink/monospaced `DESIGN.md` direction with the approved denim and cream system. Mobile tokens now use cream/denim, while green/orange/red are documented and retained only for semantic status feedback.
- **R-12:** Ordinary web panels and mobile `GlassCard` surfaces use border and tone separation rather than a universal shadow. Floating navigation retains its shadow to indicate overlay depth.
- **Automated checks:** 35 frontend tests passed, including source-level regression checks for mobile contrast and shared-card elevation. Dart formatter parsed the touched Dart files without syntax errors, but reports two files would be reformatted; I left those broader formatting changes untouched. Flutter widget tests could not start because the OneDrive-backed `mobile/.dart_tool/version` file timed out while reading. Next.js production build and `git diff --check` also could not complete because CloudStorage returned `ETIMEDOUT` while reading source/generated files. These are environment read failures, so the full web build and Flutter widget test remain unverified.
